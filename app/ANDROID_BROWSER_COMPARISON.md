# Androidとブラウザの実PDF比較（2026-11-07）

## 更新：組み立てをブラウザ版と同じ方式に変更（同日・後半）

前半の比較（下記）で、Androidは6曲中2曲しか完成しなかった。原因を切り分けるため、
Androidが読み取った記号列をそのままブラウザ版（Python）の組み立て・後処理に通したところ、
ブラウザ版と同等以上の精度になった。**記号の読み取りはほぼ同等で、差の大半は
段組み判定・編成判定・組み立て・後処理にあった。** そこで次の3点をAndroidに移植した。

- **段組み判定（Kotlin `omr/PageLayout.kt`）**：ブラウザ版 `choir_omr/systems.py` と同じ画像規則。
  背景補正＋大津の二値化（`StaffCanvas.inkMask`）、左端の縦線（組段の小節線・括弧・ブレース）で
  五線を段にまとめる、字下げした段の結合、縦線がないページの間隔判定、ブレースによるピアノ段の特定。
  Android独自の追加は2つ：五線5本の線がほとんど黒くない「五線」（裏写り・部分的なossia）の除外
  （傾きに強い区間ごとの照合）、3段にまたがるブレースによるピアノ3段の判定（homrの大譜表読み取り相当）。
  Androidの五線の左端推定がずれる場合に備え、縦線とブレースは両方の五線の左端の周りで探す。
  Python参照実装は `scripts/mobile_layout_reference.py`。
- **組み立て（Dart `lib/score_structure.dart`）**：`choir_omr/structure.py` の移植。段ごとの声部・ピアノの分離、
  声部数の多数決、音部記号からの編成判定（G G F F → TTBB など）、ピアノだけの段への休符補完、
  段内の小節数の多数決と断片小節の除外、テノール（ト音記号）のオクターブ指定。
- **後処理（Dart `lib/score_postprocess.dart`）**：`choir_omr/postprocess.py` の移植。調号・拍子の多数決、
  小節長の合意による拍子推定、リズム修復（連符・付点の再解釈の動的計画法）、小節長の正規化、
  オクターブ補正、タイ整理、音域補正、空小節の補完。

アプリの変換（`main.dart`）と実データ用テストは `lib/browser_assembly.dart` の `assembleLikeBrowser` を使う。
既存の保存済みページ（段組み情報なし）は、モデル推論をせずページを描画し直して段組みだけ追加する。
声部名のOCRは編成判定に使わなくなった（ブラウザ版と同じく音部記号と段構成で判定）。

### 追記（2026-11-08 夜）：ピアノの誤りの内訳と大譜表タイミング

評価用6曲のピアノ（正解約6,100音）で、取りこぼした音の内訳を見た（`work/parity-exp/piano_errors.py`）。

| 小節の扱い | 小節数 | 再現率 | 取りこぼし |
|---|---|---|---|
| 両手とも長さが合う | 643 | 93.4% | 316 |
| 休符で補った | 82 | 68.7% | 203 |
| リズム補正（三連符化など） | 34 | 67.0% | 111 |
| 音価を半分にした | 39 | 70.8% | 49 |
| はみ出しを切り捨てた | 16 | 38.5% | 88 |

取りこぼしの約6割は、トークンの長さが小節に合わない2割の小節に集中する。
原因は、片手の中の2声部を1列に読む、両手にまたがる連桁、音価の読み違い（8分を16分など）。
三連符の小節は、音を落とすより拍の位置がずれる誤りが多い。

**大譜表タイミング（`lib/grand_staff_timing.dart`）。** デコーダが記号ごとに出す注目位置（ONNXの`attention`出力、homrの記号座標）を、ページのx座標として記録する。
長さが合わない小節に限り、次の順に処理する。採用は、小節をちょうど埋める場合だけ。

1. 両手を横位置の順に並べ、homrの大譜表と同じカーソル（次の音の終わりまで進める）で読む。
2. 片手だけがはみ出す場合は、合っている手の音を目印に、はみ出した手の開始位置を横位置から内挿する。重なる音は別声部として残す。

声部の長さが合う手のタイミングは変えない。

| 6曲・ピアノF1（PCでAndroidと同じ切り出しを再認識） | なし | あり |
|---|---|---|
| 平均 | 87.78% | 88.00% |
| score5 / ashita | 88.7 / 82.5 | 89.1 / 83.7 |
| tanpopo | 78.0 | 77.7 |

効果は小さい（+0.2点）。夕暮（正解データなし）でも補正の入る小節数はほぼ変わらなかった。
残りの多くは、記号そのものの読み違いである。
横位置は新しく変換したページだけに記録する。キャッシュ済みのページ（横位置なし）では処理しないので、結果は以前と同じになる。

**認識側の試行（PC、同じモデル、学習なし）。**

| 方法 | 6曲ピアノF1 | 備考 |
|---|---|---|
| 基準（貪欲デコード＋大譜表タイミング） | 87.88% | |
| 段を小節線で左右に分けて読む | 61.1% | 半分を拡大すると、五線がhomrの学習時の約1.7倍の大きさで写り、読めなくなる。打ち切り。 |
| ビームサーチ8本、小節の長さ一致にボーナス10 | 87.42% | 長さを無理に合わせて誤る（tanpopo −3.7）。 |
| ビームサーチ8本、ボーナス2 | 88.44% | score5 +2.2、tsubaki +1.2。悪化はashita −0.1のみ。 |
| ビームサーチ4本・上位3候補、ボーナス2 | 88.38% | ほぼ同じ効果で、計算量は半分。 |

ビームサーチは、貪欲デコードで声部と長さが合わない小節を含むピアノの段だけをやり直す（`work/parity-exp/beam_experiment.py`）。
小節線を出した時点で、その小節の長さが同じ段の声部の多数決と一致する候補にボーナスを与える。
長さの合わない小節の数が減り、小節数が変わらず、最後まで読めた場合だけ置き換える。
PCでは、やり直す段は1段あたり貪欲デコードの約3倍の時間がかかった。6曲全体では、認識時間が約4割増える見込み。
デコーダのONNXはバッチ次元が1に固定なので、候補は1本ずつ計算するしかない。

**試して採用しなかったもの：小節単位の切り出し選択。** 縦の余白を変えた再認識（4・6・8間隔）から、長さが合う読みを小節ごとに選ぶ方法。
6曲のピアノで+0.28点（score5は+1.5点）だった。端末ではピアノの段を最大2回余分に認識することになるため、見送った。

## 前半の記録（組み立て変更前）

現状のAndroid版は、ブラウザ版と同等の認識・楽譜組み立てを達成していない。
既存6曲・51ページで、通常の編成自動判定から楽譜完成まで到達したのはAndroid 2曲、
ブラウザ6曲。ブラウザでも「あした」は86/89小節で、不一致が残る。
完成と原譜一致は別に判定する。

## 対象と条件

`choir_omr.bench.discover_samples`で既存の正解MuseScoreと対応する
`score5, nekojarashi, tanpopo, shion, tsubaki, ashita`を選んだ。
PDFと正解ファイルのSHA-256を`manifest.json`に保存した。
正解は評価のみに使用し、編成・小節数・音符を正解から認識結果へ補わない。
追加取り込みコーパスの未確認ペアを、この正解セットに混ぜていない。

- Android: API 35・x86_64エミュレーター`emulator-5554`。
  0.1.8+9の製品認識コードを使用し、debug版の`StaffBenchmarkActivity`で実PDFを入力。
  製品の`PdfOmrEngine`、`PageTextReader`、`AutoEnsembleDetector`、
  `OmrPageAssembler`、`ScoreDocument`を通した。
  全曲の組み立て・再生データ生成・MIDI/MusicXML出力を、実データのFlutterテストで試行した。
- ブラウザ: Web workerと同じ`choir_omr.pipeline.convert`を既存CLIから実行。
  ブラウザ画面の操作比較ではなく、認識バックエンドの比較。
  `engine=homr, preprocess=auto, ensemble=auto, piano=auto, unit=auto`。
- 両方PDFレンダリング指定300 dpi。ただしAndroidはその後幅1920 pxへ縮小する。
  推論前の画像解像度・切り出し・前処理まで同じ条件に置き換えた実験ではなく、
  各製品の経路の結果を比較した。
- 同じhomrモデル。FP32のsegnet・encoder・decoderの3ファイルは、
  PCの実ファイルのハッシュとAndroid `ModelStore`の検証値がすべて一致。
  encoder/decoderは396、segnetは308。
- 共通評価器`choir_omr.evaluate.compare`を使用。
  小節番号固定の`index`対応、四分音符の1/8拍の許容誤差。
  小節数不一致を位置合わせで隠すDTWは使用しない。
  ピアノ右手が複数段に分かれる参照譜は、共通評価器の同役割統合を両版に同じように適用する。
- Androidの製品キャッシュ・五線チェックポイントは有効。
  たんぽぽは前回検証した同じPDF・300 dpiの6ページキャッシュを再利用した。
  他曲も、同じ五線画像のチェックポイントがあれば再利用する製品仕様である。
  全ページのデコーダーを必ず新規実行する性能実験ではない。
  PCは既存のページ認識キャッシュを指定せず実行した。
  同時実行・異なる実行環境のため、処理時間の優劣は比較しない。

## Androidで確認した差

- **score5：第2テノールの実音補正が欠落。**
  OCRの`Tenori II E` / `Tenori TT`を声部名として認識できず、
  第2声部を「声部 2」として保存した。テノールの1オクターブ下げる補正が適用されず、
  第2声部の通常音高F1は0%。音符列を変えず、ブラウザが推定した声部名だけで
  再組立すると全体F1は89.94%、歌声96.27%になる。
  これは原因切り分け用の手動指定結果であり、通常結果79.62%の代わりに扱わない。
- **nekojarashi：薄い裏写りを余分な五線として検出。**
  1ページのピアノ導入は2段＋2段＋6段だが、Androidは11本を検出し、
  最初の段を3本として組立停止。原譜に検出位置を重ねて誤検出領域を確認した。
  4ページ13本、10ページ14本という検出も記録した。
- **shion：ピアノ3段を扱う編成判定に未対応。**
  各ページ14本（4声＋ピアノ3段の2段組）を検出できたが、
  「4声・無伴奏」と推定し、残り3本の群で停止した。
  ブラウザはピアノの複数右手段をまとめた31小節を出力した。
- **tsubaki：伴奏を声部として扱う編成誤判定。**
  4声＋ピアノの譜面を「6声」と推定し、1ページのピアノだけの2本の段で停止した。
  最終ページは11本を検出しており、ブラウザの画像レイアウト12本とも違う。
  編成判定を直すだけで全曲が通ることは未証明。

## 追記（2026-11-08）：テンポの自動読み取りと、途中から加わるパート

### テンポ（`lib/tempo_marks.dart`）

声部名用のOCR（ML Kit）の文字列から、最初のテンポ表記を読む。対象は、五線のあるページのうち最初に表記が見つかったページで、そのページの一番上にある表記を使う。

- **形の判定：** 音符の文字、「=」、「ca.」のいずれかが2〜3桁の数（30〜240）の直前にあるものをテンポ表記とみなす。
- **OCRの読まれ方：** ♩は「J」と読まれる。音符が落ちて「=ca.72」「.-76」（♩.=76）「Cn、108」となることもあるので、それぞれのパターンを用意した。
- **付点：** 付点（♩.）は1.5倍して4分音符換算にする。6/8・9/8・12/8で付点が読めなかったときは付点4分とみなす（150以上なら8分音符とみなす）。「d」は誤読が多いため（紫苑では♩を「d」と読んだ）、2分音符とはみなさない。
- **読めないとき：** 80にして警告を出す。途中のテンポ変更は扱わない。

| たんぽぽ | ♩=ca.108 | `Cn、108` | 108 |
| ねこじゃらし | ♩=ca.120 | `J=ca. 120` | 120 |

## 追記（2026-11-11）：タイの読み取り

ピアノのタイがほとんど再現されていなかった。homr はタイをスラーの記号として出すので、「隣り合う2音を同じ音高でつなぐスラー」をタイとみなしている。この判定に3つの穴があった。

1. **和音を対象外にしていた**：PC版の規則をそのまま移植したため、単音どうししかタイにしていなかった。ピアノのタイは多くが和音（例：左手のオクターブを小節線をまたいで伸ばす）なので、ほぼ全部が落ちていた。共通の音高をもつ和音どうしもタイにした。再生は音高ごとにつながるので、つながるのは共通の音だけ。MusicXML 出力も共通の音高にだけ `<tie>` を付ける。
2. **拍子記号のない段で小節線をまたぐタイが落ちていた**：拍子記号は最初の段にしかないため、2段目以降は4/4とみなされる。2/4の曲では小節の長さが合わず、小節線をまたぐタイが「隣り合っていない」と判定されていた（ねこじゃらしの合唱で74本中2本）。小節の長さは音符から求めるようにした。
3. **段をまたぐタイを捨てていた**：homr は段ごとに読むため、段の終わりのスラー開始と、次の段の頭のスラー終了が別々に残り、両方とも捨てていた。目印として残し、段をつないだあとで、小節の最後で終わる音と次の小節の頭の音が同じ音高を共有していればタイにする（`joinSystemTies`）。対にならない目印は消す。

6曲（参照あり）でのタイの数（認識/参照）と、タイの続きの音を両側で除いた音符F1（`work/parity-exp/tie_eval.py`）：

| | ピアノのタイ | 合唱のタイ | ピアノF1（タイ除外） | 合唱F1（タイ除外） |
|---|---|---|---|---|
| 変更前 | 20/127 | 197/333 | 86.51 | 94.35 |
| 変更後 | 101/127 | 313/333 | 87.81 | 96.28 |

通常の音符F1は全セットで変化なし（six 91.94、roman 97.18、pairs-clean 97.08）。Hymnus ad Caritas（30ページ）のピアノのタイは、右手が0本から27本、左手が1本から29本になった。テストは `test/tie_recognition_test.dart`。
