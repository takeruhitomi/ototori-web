# 音鳥（Choir OMR Android）

## 0.2.0: アプリとしてのUI

アプリ名を「音鳥」とし、アイコンの紺 `#1E2A6E`・金 `#F2C12E`・橙 `#E39A1C` を基調にしたカラーセット（ライト／ダーク）を `lib/app/theme.dart` にまとめました。対応OSは Android 13 以上（minSdk 33）です。

画面は下部タブの4つです。

- **変換**: PDFを選び（複数選ぶと順番にまとめて変換）、パート構成（標準は自動認識）を確認して音源を作ります。完了した楽譜はライブラリに自動保存し、1件のときはそのまま練習画面で開きます。途中で止まった変換はここから再開できます。
- **ライブラリ**: 保存した曲の一覧と検索です。「新しく変換」ボタン、MusicXML・MIDI（全体／合唱のみ／パート強調／マイナスワン／1パート）・バックアップの書き出し、名前の変更、削除ができます。
- **練習**: 原譜を見ながら再生します。今の小節に色を付けて再生位置を追い、譜面の小節をタップするとそこへ移動します。下部の再生バーにシーク、前後の小節、ループ、テンポ（手入力・タップ入力。テンポ記号は読み取っていません）、メトロノームを置いています。ミキサーは右端からスワイプするか再生バーのボタンで開く右側のパネルで、ふだんは閉じて譜面を広く使います（タブレットでは開くと譜面の横に並びます）。パートごとの音量・ミュート・ソロ・音色、「自分のパートを強調／抜く」、メトロノーム音量とカウントインを設定します。設定は曲ごとに自動保存します。
- **設定**: 外観（自動／ライト／ダーク）とカラー（音鳥・くっきり・みどり・さくら）、認識モデルの状態、ライセンスです。認識モデルはアプリに組み込み、アプリの更新と一緒に更新します。

### 音を直す（小節エディター）

練習画面の「音を直す」、譜面の小節の長押し、要確認一覧の小節名から開きます。1小節ずつ直す画面です。

- 上：原譜からその小節を切り出し、認識した音符を符頭の輪郭として重ねます（`SCORE_OUTPUT_FOR_UI.md` の `bounds` と `place` を使用）。原譜で符頭が見つからなかった音はオレンジで示し、「次の要確認」でそうした音のある小節へ移れます。選んだ符頭は上下にドラッグすると音の高さが変わり、休符の印をドラッグするとその高さの音符になります。
- 中：選んだパートのその小節を簡易な五線譜で描きます。位置情報のない認識結果（2026-11-08より前の変換や補った休符）でも、ここから選んで直せます。
- 下：選んだ音の道具。1つ上・下（調に沿って）、半音、オクターブ、休符にする／音符にする、2つに分ける（付点は音符と付点にも分けられる）、次とつなぐ、和音の音を足す・消す。

どの操作も小節の長さを変えません。抜けていた音は「分ける」で枠を作ってから高さを決めます。編集履歴は小節ごとの変更前後をIDつきで保存するため（`_choir_mobile_history` 版4。音高だけなら従来の版3）、開き直しても元に戻せます。練習画面の再生位置の線も、小節線と音符の位置がある小節ではそれに沿って動きます。

練習画面では、認識した符頭を原譜の上に灰色の細い輪で重ねます（標準でオン。「その他」メニューの「認識した音符を重ねる」で切り替え）。輪が印刷された符頭からずれている所が、認識が違う所です。原譜で符頭が見つからなかった音は輪を太くし、調にない臨時記号は小さく添えます。高さは小節の両端で測った五線から求めるため、少し傾いた原譜でも小節ごとに追従します。

### 曲の共有

練習画面の「その他」→「共有」、またはライブラリの曲の「共有」で、楽譜・直した内容と履歴・原譜PDF・認識結果を1つのファイル（`曲名.ototori`、中身はバックアップと同じZIP）にまとめ、Androidの共有シート（LINE、Googleドライブなど）で送ります。受け取った人がファイルを開くか音鳥へ共有すると、中身を検証してから「曲を受け取りました」と表示し、ライブラリに追加します。同じ曲（同じ文書ID）がすでにあるときは「置き換える」を選べ、その場合も受け取った側のミキサー・テンポなどの練習設定は残ります。担当者が1人で直して全員に配る使い方を想定しています。

再生音は、音が重なって合計が大きくなったときに波形の頭を切っていたため、ビリビリと濁っていました（0.2.1まで）。0.2.2から、2ミリ秒先を見て全体の音量をなめらかに下げるリミッター（`AudioLimiter.kt`）に替えています。

エミュレーターでの確認: 標準の `-gpu swiftshader` では原譜PDFの表示時にエミュレーター自体が終了しました。原譜表示を確認するときは `-gpu host` で起動してください。デバッグAPKは `./mobile.ps1 run` で起動します（APKを直接起動するとエンジンが起動しませんでした）。

音声フォーカス喪失・イヤホン切断通知・アプリ画面から離れた場合に一時停止し、理由を表示する処理を追加しています。割り込み後は自動再開せず、ユーザーが「再開」を押します。音量ボタンはメディア音量を操作します。この版は前面での音取り用で、バックグラウンド再生には対応していません。共通側の状態テストとAndroidビルドは通っていますが、実際のイヤホン・Bluetooth・通話による検証は未完了です。実装は Android の[音声フォーカス](https://developer.android.com/media/optimize/audio-focus)と[出力切り替え](https://developer.android.com/media/platform/output)の仕様を参照しています。

ピアノは Alexander Holm による [Salamander Grand Piano](https://github.com/Tonejs/audio/tree/master/salamander) の録音を使用しています（[CC BY 3.0](https://creativecommons.org/licenses/by/3.0/)）。一部の音を選択し、モノラル・22,050 Hz・最長 8 秒に変換しています。隣接する音高はリサンプリングで生成します。現状、録音の長さを超える音はその先が無音になり、ペダルや音の強さによる音色変化もありません。

「MIDIを書き出す」は全声部の演奏を反復順に展開し、タイ・小音符を含む試聴用の時刻で type 1 MIDI に保存します。テンポは画面の設定を使い、音量・ミュートは適用しません。歌声部は各トラック、ピアノ上下段は１トラックにまとめます。同一パート・音高の音が重なった場合は発音区間を統合します。記譜を復元するための MusicXML の代替ではありません。書き出し先は端末の保存ダイアログで指定します。

「MusicXMLを書き出す」は元の小節順の音高・音価・声部・調号・拍子・タイ・スラー・反復・括弧を記録します。ピアノは上下２段の１パートです。異名同音の綴りは元データにないためシャープを用いて再構成します。手動の反復上書き設定は未対応で、該当する場合はエラーを表示します。MusicXML の保存ダイアログを通した実行時の書き込みは未検証です。

## 開発環境の準備と実行

`.\mobile.ps1 build apk --release ...` は、ビルドが成功するとモデル同梱の arm64 APK を `work/choir-omr-<版>-models-arm64.apk` に置き、rclone で Google ドライブの「グリークラブ/音鳥」へアップロードします（`upload-apk.ps1`。同じ版のファイルは上書き、rclone のリモート名は `ototori-drive`）。アップロードしない場合は `--no-upload` を付けます。

個人の実機検証向けに `work/choir-omr-models-arm64-release.apk` を用意しています。ARM64専用・モデル同梱のリリースモードで約202MBです。開発用署名のためストア配布用ではなく、実機での速度・音質は未測定です。従来のデバッグ版は `work/choir-omr-models-debug.apk` です。

個人検証用にモデルを同梱する場合、このディレクトリで以下を実行します。通常のビルドでは同梱しません。同梱版は初回認識時にモデルをアプリ専用領域へ展開・検証します。ZIP の手動選択は不要です。

```powershell
$env:CHOIR_MODEL_BUNDLE=(Resolve-Path ../../work/mobile-model-bundle/homr-0.7.zip).Path
./mobile.ps1 build apk --debug --no-pub
```

モデル同梱は公開配布の許諾を意味しません。[homr の公式 FAQ](https://github.com/liebharc/homr/blob/main/LICENSE_FAQ.md) は、コードと重みの AGPL、および学習データ由来の条件の不確実性を説明しています。

Flutter SDK と Android SDK コマンドラインツールを用意します。Android Studio 本体は必須ではありません。Android 端末の USB デバッグを有効にし、端末に表示される認証要求を許可します。`flutter devices` に端末が表示されることを確認してください。

このディレクトリで以下を実行します。

```powershell
flutter pub get
flutter test
flutter run
```

ビルド後の APK が必要な場合は `flutter build apk --debug` を使います。Flutter・Android SDK のバージョンは初回ビルドと実機測定の際に記録し、互換性を確認してください。

この作業環境では SDK を Git 対象外の `work/mobile-sdk` に配置しています。PowerShell から `./mobile.ps1 test`、`./mobile.ps1 devices`、`./mobile.ps1 run` のように実行すると、その SDK とキャッシュを使います。Windows 全体の PATH は変更しません。

## 測定上の注意

- 各ページを別々に計測します。描画時間にはビットマップ生成と PDF の描画が含まれ、縮小・PNG 化は含まれません。
- 大きなページはメモリ枯渇を避けるため 4,000 万画素を上限にしています。上限は実機性能に基づく推奨値ではありません。
- PDF はアプリ専用領域へ取り込み、保存した変換ジョブから再度開けます。原本は変更しません。推論が完了したページの記号列も保存し、同じ内容の PDF・解像度・認識処理バージョンなら再利用します。アプリの削除やデータ消去で取り込んだ原譜・ジョブ・楽譜は失われます。
- 端末の回転や OS による Activity の再生成時は、ファイルを再選択する必要があり、書き出していない編集は失われる可能性があります。
- 実機検証では同じページの 300 / 400 dpi、連続実行時の時間・発熱、および別途取得したピーク RAM を記録してください。将来の推論については PC 基準とのトークン・音高・長さの比較も必要です。

モデルの準備方法と移植の制限は [移植状況](MODEL_PORT_STATUS.md) を参照してください。標準ビルドではモデルZIPを別途読み込みます。ローカル検証用の `choir-omr-0.1.5-models-arm64.apk` にはモデルを同梱し、初回認識時に展開します。重みは Git に含めません。homr のライセンス情報は `third_party/homr/` にあります。モデル重みを含む配布条件は引き続き確認が必要です。

## iOS 版（開発中）

iOS 版は `ios-prototype` ブランチで開発しています。画面は Flutter の `lib/` をそのまま共用し、認識・PDF 描画・音声・保存のネイティブ側は iOS 固有の実装が必要です。`ios/` の雛形と CocoaPods 設定（ONNX Runtime 1.24.1、OpenCV 4.13.0）は整備済みですが、**Swift 実装はまだビルド・実機検証を一度も行っていません**。macOS 上での実装と検証の手順は [iOS版 移植計画](IOS_PORT_PLAN.md) を参照し、検証記録が追記されるまでの iOS コードは未検証として扱ってください。Android 版と同じ理由で、モデル重み・ZIP は Git に含めません。
